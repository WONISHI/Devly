# Devly 开发阶段与交付计划

## 1. 交付目标与当前状态

把 Devly 实现为一个本地桌面编程助手：用户打开项目，输入需求，Agent 可以检索和修改代码、执行验证；用户可以查看工具过程、作出审批决定、检查差异、管理会话，并在应用重启后继续工作。

已确认技术栈：**Electron + React + TypeScript + electron-vite + 用户指定的 AI Elements（elements.ai-sdk.dev）+ 配套 shadcn/ui + Tailwind CSS + Lucide React + Zustand + Codex App Server**。

- AI 业务组件采用用户指定站点的组件源码，包括原 Commit、Conversation、Message、Tool 等，不自动替换成迁移后的另一套实现。
- 基础按钮、菜单和弹窗使用 AI Elements 配套的 shadcn/ui。
- 组件职责、进程边界和存储方式以 [技术选型](../tech-stack.md) 与 [架构设计](../architecture.md) 为基线。
- 当前工程已初始化并安装依赖，具备基础桌面界面、打开目录和环境检测，以及原 AI Elements 预览。详见 [搭建记录](../setup.md)。阶段状态按完整验收标准记录，基础搭建完成不等于整个阶段完成。

默认先在当前 macOS 开发环境实现，再验证 Windows。1.0 验收范围按 macOS 与 Windows 安排；Linux 作为后续平台扩展。平台范围属于本计划的执行假设，可随产品要求调整，不能用跨平台源码代替目标系统验证。

### 两个主要验收节点

- **MVP：阶段 0–6 完成。** 能打开 Git 项目、与 Codex 对话、处理审批和取消、修改真实代码、展示验证结果并查看最终差异。阶段 3、4 已提供基本会话持久化与重启后恢复；异常执行状态恢复在阶段 8 完整验收。
- **完整 1.0：阶段 0–10 完成。** 在 MVP 基础上具备交互终端、恢复能力、多任务隔离、约定集成与经过目标平台验证的安装包。

## 3. 阶段 0：技术贯通验证

**目的：尽早验证高风险依赖和真实执行链路，给后续开发建立可复现基线。**

实施内容：

- 在临时验证工程中确定 Electron、开发机 Node.js、pnpm、React、Tailwind 与 AI Elements 配套依赖的兼容组合。
- 按需引入原 Conversation、Message、Tool、Commit 组件，确认本地渲染；记录源码来源、版本或提交信息和依赖清单。
- 启动本机 Codex App Server，完成初始化、创建测试会话、接收文本和执行事件；确认认证、审批、中断和历史读取的可用协议。
- 验证原生依赖 better-sqlite3、node-pty 在目标 Electron 中加载。
- 验证 Monaco Worker 和编辑器资源本地加载。
- 提前制作最小打包产物，在安装包中验证资源与原生模块位置，并安排 Windows 对应平台验证。
- 记录所选 Codex 版本支持的权限、模型选择、MCP 和 Skills 配置入口；后续集成以实际能力为准。

验收标准：

- [ ] 能演示一个真实 Codex 回合，界面组件可以展示返回内容。
- [ ] 原 Commit 组件展示测试提交信息，所选依赖版本可复现安装。
- [ ] SQLite、PTY、Monaco 在开发环境和已验证平台的最小打包产物中工作。
- [ ] 已形成版本清单、验证记录、已知限制和后续平台验证事项。

这一阶段的测试数据只用于演示与技术验证，后续正式界面不得把模拟结果显示成实际执行结果。

## 4. 阶段 1：工程结构与进程通信

实施内容：

- 用 electron-vite 初始化 main、preload、renderer 与 shared 目录，建立按功能组织的代码结构。
- 配置 TypeScript 严格模式、路径别名、ESLint、Prettier、pnpm 锁文件和构建脚本。
- 建立受限 IPC：共享类型与 Zod 校验、固定业务方法、统一错误格式和事件订阅清理。
- 配置 Renderer 隔离、主窗口生命周期、应用退出和后台进程清理。
- 建立 Agent 适配器接口和统一应用事件，不把 Codex 协议类型散落到界面组件。
- 添加针对协议解析和 IPC 归属的基础测试工具，建立持续集成检查入口。

验收标准：

- [ ] 新环境可以按文档安装、启动、检查类型和构建。
- [ ] 界面能通过受限 IPC 调用一项真实主进程服务，非法参数得到明确错误。
- [ ] 关闭窗口和退出应用时没有本阶段创建的后台进程或事件监听器残留。

## 5. 阶段 2：桌面布局与组件体系

实施内容：

- 实现项目侧栏、会话列表、对话区、右侧编辑区域、底部面板与可调整布局。
- 接入用户指定的 AI Elements 原组件，建立统一的业务封装和展示样例。
- 实现 Conversation、Message、Prompt Input、Tool、Plan、Confirmation、Commit 等组件的空、加载、成功和错误状态。
- 配置 Lucide 图标、Tailwind 主题变量、明亮/暗色/跟随系统、紧凑组件密度。
- 实现键盘焦点、常用操作快捷键、消息复制和基础 Markdown 展示。
- 管理 Markdown 链接与资源加载，应用主题同步到后续编辑器和终端。

验收标准：

- [ ] 主窗口缩放和面板调整后不遮挡输入区或主要操作。
- [ ] 用户指定的原 AI Elements 组件可见，主题切换保持一致。
- [ ] 展示用数据与真实会话明确区分；本阶段不宣称已完成 Agent 能力。

## 6. 阶段 3：项目、设置与本地数据

实施内容：

- 实现打开目录、最近项目、路径失效提示、项目移除和当前工作目录展示。
- 建立 SQLite Worker、Repository 层和版本化迁移，保存项目、设置和会话映射。
- 建立会话列表、新建、重命名和归档等元数据能力，明确本地与引擎 ID 的映射关系。
- 实现文件树按需加载、只读预览和变化刷新，处理不存在、无权限及过大文件。
- 实现设置界面：Codex 可执行文件路径、主题、默认执行策略和日志入口；连接能力尚未就绪时显示明确状态。
- 保存面板布局等轻量偏好，避免将完整消息与执行日志全部写入前端持久化状态。

验收标准：

- [ ] 打开多个项目时，会话索引和工作目录不混用。
- [ ] 重启应用后项目、设置和本地会话元数据仍可读取。
- [ ] 数据库迁移可以从上一应用数据版本升级；文件路径变化不会导致应用无法启动。

## 7. 阶段 4：Codex 运行时与会话协议

实施内容：

- 实现 Codex 路径与版本检测、启动/退出管理、stdio JSON 消息解析、请求关联和超时处理。
- 完成初始化握手、连接状态展示和启动失败诊断。
- 按实际支持的认证机制实现登录入口、认证状态刷新、失效提示和重新连接；凭据不交给 Renderer 保存。
- 实现创建、读取、恢复会话，以及回合开始、事件订阅和引擎 ID 映射。
- 从实际协议能力提供模型、权限和运行配置，不能展示不可用但可点击的配置。
- 将 Codex 事件统一为应用事件，建立基本历史读取和重启后的正常会话恢复。

验收标准：

- [ ] 从界面提交真实输入并持续显示真实模型输出。
- [ ] 认证失效、Codex 未安装、版本不兼容和进程退出都有明确处理。
- [ ] 重启后能恢复对应会话的历史，并在正确项目目录继续发送消息。
- [ ] 重复挂载界面不会产生重复消息或重复执行。

## 8. 阶段 5：Agent 对话、工具过程、审批与取消

实施内容：

- 将文本增量、工具输入/输出、计划、引擎提供的摘要和错误映射到 AI Elements 组件。
- 实现回合级状态机和工具级状态；展示排队、处理中、等待审批、完成、失败和中断。
- 实现审批请求队列、请求 ID 关联、操作范围展示、允许和拒绝，并防止重复响应。
- 实现停止按钮、引擎中断、停止确认和无法确认状态的处理。
- 明确首版执行中再次输入的策略：默认不启动同一会话的第二个并行回合，后续队列在阶段 9 完成。
- 实现真实测试和构建结果的基础展示，区分失败、未执行和未验证。
- 对流式文本采用批量更新，避免整个会话随每个字符重渲染。

验收标准：

- [ ] 在样例项目中完成“定位问题 → 修改代码 → 执行测试”的真实过程。
- [ ] 同意或拒绝审批仅影响对应操作，拒绝后能够继续或明确结束。
- [ ] 取消后等待执行端确认，保留已有修改并提示查看差异。
- [ ] 界面展示的工具结果、测试状态与实际输出一致。

## 9. 阶段 6：文件编辑、Diff 与 Git 展示

实施内容：

- 接入 Monaco 文件编辑、保存、标签切换和本地修改状态。
- 实现文件版本检查、外部变更提示和冲突处理，保护用户已有修改。
- 获取 Git 状态、工作区差异、暂存区差异、提交记录及提交文件变更。
- 使用原 Commit 组件展示实际提交 hash、作者、时间、文件状态和增删行数。
- 使用 Monaco Diff 展示真实前后内容，正确处理新增、删除、重命名及不支持预览的文件。
- 区分任务开始前的修改和执行期间观察到的修改；并发编辑时无法可靠归因的内容明确提示。
- 提供明确的暂存、取消暂存、填写消息和本地提交操作；用户点击后才执行，操作前刷新状态。

验收标准：

- [ ] Git 页面与 Git CLI 的状态和差异一致，Commit 卡片展示真实提交。
- [ ] 能从修改文件清单跳转到对应 Diff，并检查 Agent 的真实修改。
- [ ] 文件外部变化时不会静默覆盖用户编辑。
- [ ] 非 Git 项目仍可聊天和查看文件，Git 功能显示对应说明。

**阶段 6 完成后交付 MVP，邀请实际使用并根据反馈修正后续工作量。**

## 10. 阶段 7：交互式终端与执行结果

实施内容：

- 接入 xterm.js 与 node-pty，支持新建、切换、关闭、输入、尺寸同步和滚动。
- 按项目管理终端工作目录，明确用户终端与 Agent 执行进程各自的生命周期。
- 处理 Shell 退出、Ctrl+C、窗口缩放与应用退出后的进程清理。
- 使用 AI Elements Terminal 展示 Agent 命令输出，Test Results、Stack Trace 展示实际测试与错误信息。
- 处理 ANSI 输出、日志复制、大输出限流与日志文件落盘。

验收标准：

- [ ] 用户可在当前项目运行命令、交互输入和中断命令。
- [ ] Agent 输出展示不会被误当作可交互 Shell。
- [ ] 切换项目不串用终端目录，关闭终端后进程得到清理。
- [ ] macOS 与 Windows 的终端行为分别验证。

## 11. 阶段 8：恢复、异常与稳定性

实施内容：

- 完善事件去重、排序、消息归属和必要的历史分页。
- 应用重启或连接恢复时与引擎重新核对活动回合、待审批、文件和进程状态。
- 处理运行时崩溃、连接中断、数据库错误、磁盘写入失败及大文件限制。
- 检查任务中断后的未完成项，禁止自动重放有副作用的操作。
- 对长对话、长日志和大量工具事件做性能验证，按需接入虚拟列表。
- 完善结构化日志、导出诊断信息及敏感信息过滤，确保可定位失败原因。

验收标准：

- [ ] 执行期间断连、退出、重启后可恢复到真实状态或明确的待确认状态。
- [ ] 重连不会重复写文件、重复执行命令或错误批准旧请求。
- [ ] 长任务场景保持输入和窗口响应，输出不会无限占用界面内存。
- [ ] 用户未保存编辑、任务已有修改和失败原因可以被明确识别。

## 12. 阶段 9：多任务与扩展集成

实施内容：

- 提供多会话任务列表、等待队列、并发上限和按项目的任务状态汇总。
- 同一工作目录的写任务默认串行；需要并行修改时为任务创建独立 worktree。
- 实现 worktree 创建、分支关联、差异检查、合并入口与保留/清理流程；存在修改或运行任务时禁止静默清理。
- 接入已验证 Codex 版本支持的 MCP 配置、状态与故障提示，避免应用和引擎各自执行同一个工具。
- 接入该版本实际支持的 Skills 发现或配置入口，展示作用范围和来源，并验证会话中能够使用。
- 对当前版本不支持的能力明确记录限制，不通过模拟状态完成验收。

验收标准：

- [ ] 两个任务在各自工作区执行时，文件、会话、审批和日志均不串用。
- [ ] 排队、取消、并发限制与 worktree 生命周期可演示。
- [ ] 至少接入一个真实 MCP 服务和一个可用 Skill，完成实际调用与失败场景验证。
- [ ] worktree 修改回到目标分支时可审查，冲突明确显示，不自动覆盖用户内容。

## 13. 阶段 10：平台验收与 1.0 交付

实施内容：

- 在 macOS 和 Windows 构建安装包，验证 SQLite、PTY、Monaco、本地资源和 Codex 进程启动。
- 验证首次安装、重启、设置持久化、数据升级、退出清理和缺失依赖引导。
- 根据实际分发渠道准备签名、公证和安装说明；需要外部账号或凭据时单独记录交付依赖。
- 以冻结依赖版本完成静态检查、关键行为测试、桌面流程与真实样例项目验收。
- 修复阻断核心流程的问题，记录仍存在的限制和可复现步骤。
- 编写用户指南、开发启动说明、打包说明、数据位置、诊断方法和版本说明。

验收标准：

- [ ] 目标系统实际安装运行成功，有对应平台的验证记录。
- [ ] 完整场景“打开项目 → 发出需求 → 审批 → 修改 → 测试 → Diff → 重启继续”通过。
- [ ] 多任务隔离、终端、MCP 与 Skills 达到阶段 9 约定标准。
- [ ] 不存在未解决的核心流程阻断或已知静默覆盖用户文件的问题。
- [ ] 安装包、源码、锁文件、用户文档、版本说明和已知问题清单齐备。

目标系统或签名条件未具备时，可以交付相应平台预览构建并明确状态，但不能把尚未验证的目标平台标为 1.0 已完成。

## 14. 每阶段的执行与记录规则

- 开始阶段前确认上一阶段产物可运行，并列出本阶段功能与验收场景。
- 每完成一个可演示功能就做相应集成验证，不把连接真实引擎、原生模块与打包验证全部推到末尾。
- 按行为选择测试：重点覆盖协议关联、状态流转、权限、恢复和数据写入，不为简单样式变化编写重复实现的测试。
- 阶段结束记录改动、演示方式、验证结果和已知限制，并在本计划更新状态。
- 演示数据、工具返回结果、模型文字和真实系统状态分别标明来源；不以模型口头成功代替执行验证。
- 阻塞项记录所需条件、影响范围和可独立推进的工作；未通过验收的阶段保持未完成。

## 15. 1.0 完成定义与后续范围

只有在阶段 0–10 的适用验收项全部完成、目标平台有真实运行证据、文档与安装包一致时，才把 1.0 标为完成。

以下作为后续独立版本，不自动扩展本次交付范围：

- 自研 Agent 引擎与多模型供应商适配。
